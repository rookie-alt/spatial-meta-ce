# 导师汇报讲稿：面向空间漂移的结构锚点基数估计

> 2026-11-08。全部数字来自 `实验文档/115、117、119、120` 的已归档服务器实测；估计值未写入。
> 讲稿约 10 分钟，每节标注时长。**加粗的限制句请务必说出来**，否则结论会被高估。

---

## 0. 一句话结论（30 秒）

我们放弃了「PG 输出 + 残差修正」的模型形式，改用**零参数的结构恒等式**做锚点。

源库 2–7 表上它全部赢 PostgreSQL；但四个目标库上，整体不如我们原来的 PG 锚模型。

所以现在的判断是：**结构恒等式是一条可靠的诊断工具和强基线，还不是一个能替换 PG 的估计器。**

---

## 1. 问题与已有诊断（1.5 分钟）

**课题**：跨数据库基数估计，本轮只做空间漂移。时间漂移、上下文学习、PG 插件都不做。

**数据边界**（三条红线，全程未破）：

| 角色 | 库 | 用途 |
|---|---|---|
| 训练 | 23 个 | 训练 |
| 源验证 | chembl / legalacts / telstra | 超参、checkpoint 选择 |
| 目标库 | imdb / stats / genome / ergastf1 | 只做最终评估的推理输入 |

目标库**不进训练、不进超参、不选 checkpoint、不早停**。

**旧模型（ERM-sum，PG 锚 + 残差头，132,545 参数）的结果**：

- 12 个 seed×库组合，**Q95 全部输 PRICE**，PRICE/ours 中位 0.561。
- 对 PG 9/12 赢。

**为什么输**——三层诊断，逐条排除了：

| 假设 | 检验结果 |
|---|---|
| 校准问题 | 否。bias 中位在 29/30 库 ±0.23 内 |
| 过度收缩 | 否。预测离散度在 22/30 库反而比 PRICE 大 |
| **排序一致性** | **是。corr 与 Q95 胜负在 27/30 库一致，且精确跟随训练曝光**（目标库 4/4 输、训练过的库 23/26 赢） |

**方向信号审计**：模型缺的是「该往哪边修」的信号。

- 库内可预测性很强：AUC 0.91–0.98。
- **跨库不迁移**：LODO AUC 0.38–0.61，telstra 系统性反向。

**另有一条方法学事实**：实测 seed 间标准差 **6.28pp**，大于我们试过的所有精度杠杆效应量。所以单 seed 筛选不可信，后面所有结论都至少三 seed。

> 结论：PG 残差路线的问题不是损失函数，是缺少可迁移的方向信号。继续调损失没有依据。

## 2. 为什么转向结构恒等式（2 分钟）

三条独立证据线，**全部只用源库原始 CSV，未读目标库**。

| 规模 | 估计器 | median | Q95 | 出处 |
|---|---|---:|---:|---|
| 2 表 600 条 | PG | 1.264 | 6.335 | 115 G1a |
| | `C_uncond`（不用 PG） | 1.067 | **2.481** | |
| | `C_cond`（精确 oracle） | 1.000 | 1.000 | |
| 3 表 400 条 | PG | 1.418 | 7.557 | 117 G2a |
| | `F_indep`（过滤后边缘） | 1.068 | **1.686** | |
| 4–7 表 600 条 | PG | 2.000 | 11.800 | tree_identity |
| | `C_uncond` | 1.502 | **9.537** | |
| | `C_cond` | 1.000 | 1.000 | |

**三个要点**：

1. **`C_cond` 与 workload `true_card` 最大相对偏差 0.0**。这证明树形组装是精确的，不是近似。
2. **`C_uncond` 零参数、不用 PG、不训练，仍然赢 PG**，且 4/5/6/7 表逐档全赢。
3. **起作用的不是条件化**。G1a 判 `conditional_signal_not_observed`（median 比值 0.937，未过 50% 门槛）；G2a 判 `blocked`（carcinogenesis 18,622 条三表查询 100% 是「两表连中表同一列」，在这种形态上二维联合构造性无收益）。

> 所以方向收敛为：**用结构恒等式本身当锚点，而不是继续追条件相关性。**

## 3. 方案设计（1.5 分钟）

```text
ŷ = log C_struct(q) + g_θ(x)
        ↑                  ↑
   结构恒等式（零参数）    小修正头（可训练）
```

`C_struct` 怎么算——在 join 树上做变量消除：

```text
SQL → join 树 + 变量类 + 过滤谓词
      ↓
   每张表一个因子（连接键计数）
      ↓
   叶子向根发消息，把不朝父节点走的变量求和消掉
      ↓
   根的 Σ = join 行数
```

**只用三件原料**：

| 原料 | 说明 |
|---|---|
| 行数 | 含非 NULL 键行数 |
| 单列键频率 | 压成 160 桶**共享边界** |
| 过滤选择率 | 只施加一次 |

**为什么必须共享边界**：PRICE 的 `histogram40` 是每张表按自己的分位数分桶，表 A 的第 7 桶和表 B 的第 7 桶不是同一段键值，不能相乘。做法是对每条连接边取两侧键值并集，在并集上定边界。

**适用范围（必须主动说）**：只支持**树形 join**。环、自连接、外连接、子查询、GROUP BY / ORDER BY / LIMIT 全部拒绝。

**五步验收**：摘要 → 桶对齐 → 锚点接入 → 训练 → 评估，每步不过就停。

## 4. 实测结果（2 分钟）

### 前四步：全部通过

| 步骤 | 门槛 | 结果 |
|---|---|---|
| ① 摘要 | 复算 `C_cond` 与精确键值逐位一致 | 600/600，`bit_identical` |
| ② 桶对齐 | Q95 ≤ 19.07 且优于 PG | **160 桶 9.736**（精确 9.537） |
| ③ 锚点接入 | 未训练模型 ≡ 闭式结果 | 逐位一致 |
| ④ 训练 | 三 seed 源验证退化 ≤10% | +3.60% / −0.63% / +6.58% |

桶数扫描：40 桶 20.551（越线）、**160 桶 9.736**、320 桶 9.684（不值得翻倍预算）。

> ② 是「有条件通过」：第一道门槛过得硬（9.736 vs 19.07），但**第二道在 n=600 下不可判定**——bootstrap 给 PG Q95 的标准差是 2.064，9.736 与 11.800 相差约一个标准差。正确说法是「与 PG 无可分辨差异」，**不能说显著优于**。

### 第五步：四目标库 K=0，负结果

| 库 | n | PG | PRICE | 旧 sum（PG 锚） | 新 struct |
|---|---:|---:|---:|---:|---:|
| imdb | 521 | 87.1 | 21.0 | 33.1 ± 1.8 | 36.0 ± 8.4 |
| stats | 2603 | 75.7 | 39.5 | 81.1 ± 2.4 | **376.4 ± 69.9** |
| genome | 1699 | 1907.3 | 31.3 | 192.0 ± 122.7 | **976.1 ± 747.8** |
| ergastf1 | 1258 | 27.6 | 15.3 | 23.4 ± 1.5 | **81.2 ± 119.2** |

**唯一稳定亮点**：imdb 的 4+ 表桶 **68.2 ± 6.7**（旧 sum 440.5、PRICE 88.9、PG 1174.9）。

> 但这是单库、118 条查询，不足以支撑全局结论。

## 5. 诊断：误差从哪来（1 分钟）

把「裸锚点误差」和「修正头残差」分开测——这是旧 PG 锚模型做不到的，因为 PG 是黑盒。

| 库 | 锚点 Q95 log 误差 | 修正头残差均值（三 seed） |
|---|---:|---|
| imdb | 3.975 | +2.34 / +2.72 / +2.54 |
| stats | 6.792 | +0.41 / +0.93 / +0.61 |
| genome | 7.930 | +0.30 / −0.03 / +3.65 |
| ergastf1 | 2.542 | +1.39 / +0.86 / +0.25 |

**两条结论**：

1. **锚点误差随表数单调增长**：stats 的中位 log 误差从 2 表的 0.586 涨到 7 表的 7.559。二表查询只有 0.227–0.586，说明摘要和数据链没坏——**弱的是多表连接上的结构估计本身**。
2. **修正头学到的几乎是源库的近均匀上移**，不是对目标库尾部的修复。它把裸锚点从「很差」拉到「较差」。

> 所以继续加修正头容量没有依据。

## 6. 必须主动交代的四个边界（1 分钟）

这四条是我认为老师最应该知道的，因为任何一条都会改变「这套东西能不能用」的判断。

1. **摘要不含过滤列**。600 条查询里 **599 条带 `WHERE`**。现在的实现里过滤掩码仍然回原表算，所以「只读摘要、不碰原表」这条链路**没有实现也没有验证**。已证明的只是「桶化 join 边缘的代价是 1.021×」。
2. **160 桶是 PRICE `histogram40` 的 4 倍存储预算**，不是同预算对照。
3. **只支持树形 join**。真实 workload 里环、外连接、子查询占比不低，这是从「能算」到「能用」最远的距离。
4. **存储和时间收益从未量化**。摘要的价值主张是「扫一遍基表，之后只读固定大小」，但精确边缘与 160 桶的存储差多少倍、第二次查询快多少，都没有数字。

## 附：可能被问到的问题

**Q：为什么不直接把 PG 估计和结构估计加权平均？**
A：试过替换，没试过融合（选项 C）。替换失败说明结构信息单独不够；融合是否更好，取决于两者误差是否互补——目标库上结构锚点与 PG 的误差相关性还没测过。

**Q：结构恒等式在源库赢 PG，为什么目标库输？**
A：两个原因。一是源库用的是原始 CSV 精确键值，目标库只能用 160 桶摘要；二是目标库查询更大、更偏斜，桶内均匀假设失效更严重。120 §6 显示误差随表数增长，正是这个机制。

**Q：这套方法能用于生产吗？**
A：现在不能。四个边界里，过滤列和树形限制是硬伤。要用于生产，必须先解决「过滤列进摘要」和「非树形 join 的近似」，两者都会显著增加存储和复杂度。

**Q：和 FactorJoin 有什么区别？**
A：FactorJoin 用 join 图上的因子分解 + 学习；我们用的是精确的结构恒等式（树上变量消除）+ 零参数边缘，不学习。相同点是共享分桶边界这个技术。差异是我们只在树上精确，FactorJoin 处理一般 join 图。
