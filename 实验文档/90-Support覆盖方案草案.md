# 90 Support 覆盖诊断与改进方案草案

日期：2026-10-19（Asia/Shanghai）。
状态：`draft / not_implemented / execution_not_authorized`。
本文件只写方案与判据，**不执行任何训练、不读取目标库、不改现有冻结协议**。

上游依据：[86 号 §7](86-低维元适应精度改进方案草案.md) 第 1 条路线、
[89 号 D1 结果](89-低维前置诊断结果.md)。88 号诊断已完成并揭示了一个 86 号
未预期的问题：**适应结果的方向由那 100 条 support 决定，而不是由数据库决定**。

## 1. 要回答的问题

在 K 固定为 20、模型、loss、lr、步数全部不变的前提下，**改变 support 的抽样方式**
能否稳定缩小适应收益的 run 间方差，并提高 4+ Q95 的期望改善？

这个问题来自 D1 的一条硬观察，不是来自"想试试分层抽样"：

| 库 | run0 | run1 | run2 | run3 | run4 |
| --- | ---: | ---: | ---: | ---: | ---: |
| legalacts low4 改善占比 | **85.4%** | 7.5% | 7.5% | 7.8% | **47.3%** |
| telstra low4 改善占比 | **67.7%** | 21.8% | **75.3%** | 23.5% | **72.7%** |

legalacts 与 telstra 的 query 全集在库内固定（49,404 / 49,900 条），五个 run 之间
唯一变化的是 `random.Random(f"{seed}:{database}:{run}").sample(indices, 100)` 抽出的
100 条 support（取前 20 条）。**方向翻转不能由查询抽样解释，只能由 support 成分解释。**

如果这条判断成立，那么任何"改进适应器"的方案（包括已暂停的 86 号）都在优化一个
被 support 噪声主导的信号；先处理 support 的方差，收益/噪声比才会改善。

## 2. 本方案不做什么

- **不改模型结构、不改 loss、不改 lr、不改适应步数、不改 K。** 这些全部冻结。
- **不重训任何模型。** 诊断阶段只用已归档 checkpoint 与缓存，纯 CPU。
- **不动 86 号。** 86 号保持 `paused_by_user`；本方案若失败，不自动复活 86 号。
- **不读目标库** `imdb/stats/genome/ergastf1`；`hepatitis/sakila` 按 86 号 §4 边界
  同样不进入开发与选择。

## 3. 分两阶段，先诊断后干预

### 阶段 A：Support 敏感性的定量归因（纯 CPU，只读）

**目的**：把 D1 的定性观察变成可检验的量——方向翻转有多大比例由 support 成分解释，
以及是否存在"只在可观测特征上"就能预测好 support 的规则。

**A1. support 特征刻画。**
对每个 (库, run) 的 100 条 support（及前 20 条），计算只依赖可观测输入的量：

| 量 | 定义 | 来源 |
| --- | --- | --- |
| 表数分布 | `{4,5,6+}` 三个桶各多少条 | `n_tables` |
| 真实基数分布 | 三分位各多少条 | `true` |
| PG 偏差分布 | `|PG − true| / true` 三分位各多少条 | `cards[:,1]` |
| 高估/低估比例 | `PG > true` 的占比 | 同上 |
| join/过滤 token 数 | 组 0/3 的序列长度均值 | 缓存 `groups` |
| 笛卡尔积程度 | 组 2 的 `log1p` 均值 | 缓存 `groups` |

**A2. 方差归因。**
把 D1 的逐 run 结果（`Δ` 的改善占比、low4 Q95 ratio）作为因变量，A1 的 support 特征
作为自变量，做**相关分析**（不是回归预测）。报告每个 support 特征与适应收益的
Spearman 相关及五 run 极差。判据：

- 若存在至少一个 support 特征与该库 adapt 收益的 `|ρ| ≥ 0.8`（n=5，只作方向提示），
  记为 `predictable_by_support_composition`；
- 若全部 `|ρ| < 0.5`，记为 `not_predictable_from_support`，此时阶段 B 的分层抽样
  失去依据，方案应停止。

**A3. 重复抽样基线（关键）。**
现有 5 个 run 是 5 次独立抽样。**再抽 45 次**（seed 固定为 1729 之外的独立序列，
不复用现有 seed）共 50 次 support，**只做前向，不训练**：用已归档的 `none` 与
`head3` 算子参数，按现有 `operator_params` 逻辑在 support 上适应、再对 query 前向。
这给出：

- 改善占比与 low4 Q95 ratio 的**真实抽样分布**（50 个点，而非 5 个）；
- 现有 5 个 run 落在该分布的哪个分位——判断 81 号报告的中位数是否只是 5 次抽样的偶然；
- 达到 95% 置信所需的 support 重复次数。

> A3 是纯推理：每个 run 一次 3 步适应 + 全 query 前向。按 D2 实测（15 个 cell
> 414 秒，含特征抓取），50 次 × 3 库的粗略量级是**数小时 CPU**，需在实现计划中
> 实测确认，不预先写进结论。

### 阶段 B：仅当 A3 显示方差主导时才做

**目的**：比较三种 support 抽样策略，K 固定 20，其余全部冻结。

| 策略 | 定义 | 只用可观测输入 |
| --- | --- | --- |
| R（random） | 现有 `random.sample`，作为基线 | 是 |
| S（stratified） | 按 A1 的表数 × 真实基数桶分层配额抽样 | 是 |
| D（diversity） | 贪心最大化 support 内特征多样性（最远点采样） | 是 |
| O（oracle，仅诊断） | 按"该查询在 head3 下是否恶化"排序后抽样 | **否，含真值/结果泄漏** |

**O 策略只用于给出上界，不参与任何候选选择**，且必须在所有输出中标注
`leakage=true`。它的作用是回答"如果完美知道哪些 support 有用，最多能拿到多少"，
从而判断 S/D 距离上界有多远。

**共享 support**：按 86 号 §7 的要求，R/S/D 三策略在同一 (库, run) 上使用
**同一批 query**，只换 support，避免 query 抽样混淆。

**判据（阶段 B，事前冻结）**：

- 主指标：`M_V(策略) = mean_over_3_db(mean_over_5_run(4+ Q95))`，与 R 比较。
- 若 `S` 或 `D` 的 `M_V` **不优于** `R` 的 `0.95 ×`（即改善 < 5%），判为
  `no_support_gain`，不进入任何后续训练。
- 若优于 `0.95 ×`，仍**不得**直接进入正式训练：须先证明收益不是由 5 个 run 的
  抽样偶然造成（用 A3 的 50 次分布做置换检验）。
- 任一策略出现库间方向相反，判 `unstable`，不提名候选。

## 5. 红线

- 目标库 `imdb/stats/genome/ergastf1` 不进任何路径、不读取、不出现在输出。
- `hepatitis/sakila` 不进入开发与候选选择（86 号 §4 边界）。
- **O 策略含泄漏，只能给上界，绝不能变成候选，也不能写进论文主结果。**
- 不训练、不占 GPU 的诊断阶段（A）可直接执行；阶段 B 涉及适应计算，须另行授权。
- 不因为"想看到改善"而放宽 5% 门槛或增加策略数量。

## 6. 执行前置

1. 本草案经用户审阅并冻结。
2. 阶段 A 需要新脚本，**另提实现计划**，不在本文件内写代码。
3. 阶段 A 完成后停下报告，由阶段 A 的判据决定是否进入阶段 B，**不自动续跑**。

## 7. 待用户在审阅时确认的四点

1. **是否接受 A3 的 50 次重复抽样**（约数小时 CPU）。这是本方案的核心证据，
   没有它，"run 间翻转是抽样噪声还是真实效应"无法区分。
2. **O 策略是否保留**。它能给出上界，但含结果泄漏，必须严格隔离。若你认为风险
   大于价值，可以删掉，方案仍成立但失去"距离上界多远"的参照。
3. **阶段 B 的 5% 门槛**是否合适。这个数值是模仿 86 号"再改善 10%"的下调版本，
   没有独立依据，应视为待议。
4. **若 A2 判为 `not_predictable_from_support`，是否直接停止**，不再做阶段 B。
   我建议是——否则阶段 B 就变成了无依据的穷举。

## 8. 本方案与 86 号的关键区别

| | 86 号 | 90 号 |
| --- | --- | --- |
| 改的东西 | 部署适应参数化（65 → 4 维） | support 抽样方式 |
| 需要训练 | 是，12,000 次更新 | 阶段 A 否，阶段 B 是 |
| 依据 | 容量-精度取舍的方向性猜测 | D1 的 run 间方向翻转硬证据 |
| 失败代价 | 8 小时 GPU + 3 臂 | 阶段 A 数小时 CPU |
| 若失败说明 | 低维参数化不适用 | support 不是主导因素，应查别处 |

本方案**不承诺**能改善精度。它的第一价值是把"支撑集方差"这个在 81/85/89 号中
反复出现但从未被量化的因素，变成一个可复现的数字。
