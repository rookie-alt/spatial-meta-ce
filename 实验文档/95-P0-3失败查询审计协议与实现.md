日期：2026-10-20
分支：`feat/accuracy-p1-loss-gate-20261019`
协议来源：[93-精度提升详细方案](93-精度提升详细方案.md) §3 P0-3、§5 M1

---

## 0. 这个审计要回答什么

93 §3 P0-3 的目标不是再选一个模型，而是**定方向**：

> 适应后恶化的查询，是否有稳定的可观测特征（表数、PG 偏差方向、直方图缺失、join 形态）？直接告诉我们缺什么输入信息。

产出的唯一用途：决定 P2-1 要加什么特征（93 §2 嫌疑 4）。

---

## 1. 冻结的定义（执行前写死，不得事后调整）

| 项 | 定义 | 理由 |
|---|---|---|
| 单条 log 误差 | abs(log_pred − log(max(true,1))) | 与主指标 `log_q95` 聚合的同一个量 |
| **恶化**（worsened） | 适应后（K>0）log 误差 **大于** PG 锚（K=0）log 误差，超出 `1e-9` 容差 | "恶化"必须是相对 K=0 的，不是绝对误差大 |
| PG 方向 | 定义在 **锚**（K=0）上：`over` = PG 高估真值，`under` = 低估，`tie` = 相等 | 用预测方向会混淆"模型错"与"PG 本来就错" |
| 表数分桶 | `1` / `2-3` / `4-5` / `6+` | 与项目 `four_plus_tables` 口径衔接 |
| 集中度 | 恶化最狠的 **1%** 查询贡献的总恶化占比 | 沿用 [88号](88-低维方案前置诊断协议草案.md) §3.3 的同一形状 |

### 1.1 集中度判据（照搬 88 §3.3 的阈值）

| top1pct_share | worsened_fraction | 形状 | 解读 |
|---|---|---|---|
| ≥ 0.40 | — | `concentrated` | 少数极端查询驱动 → 应审计这些查询的特征 |
| < 0.25 | 0.40–0.60 | `diffuse` | 系统性漂移 → 缺的是容量或特征，不是个别样本 |
| 其余 | — | `inconclusive` | 不据此下结论 |

> 88 §3.3 用这套阈值判断低维适应是否对症；本审计借用同一形状判断"缺特征还是缺容量"，**不改变阈值本身**，以便两份文档可比。

## 2. 硬边界

| 边界 | 执行方式 |
|---|---|
| **不读目标库** | `assert_source_database()` 对 `imdb/stats/genome/ergastf1` 直接抛 `ValueError`；`read_predictions()` 逐行调用它 |
| 只读 | 仅读 `predictions.csv`，只写一个新 JSON，不改任何 run 目录 |
| 不选模型 | 不产出任何"哪个 checkpoint 更好"的判断；输出只有分布与分桶计数 |
| 单文件内不混库 | `audit_rows(rows, database)` 要求一个库一个报告，避免跨库统计掩盖库间差异 |

### 2.1 关于「STATS K>0 恶化查询」

93 §3 P0-3 原文要求覆盖 STATS。**STATS 是目标库，本项目红线禁止目标库进入训练/超参/checkpoint 选择。**

这里的边界是：**只读审计不等于训练选择**。但为了让红线无歧义，本轮先做**源侧**（chembl / legalacts / telstra）的同一套审计；STATS 侧是否执行，须在拿到源侧结论后**单独征得用户明确同意**，因为一旦执行就会产生"读过 STATS"的记录，需要在论文中如实披露。

**本轮不读 STATS。** 源侧审计已经足以回答"缺什么特征"——三个源验证库在 100/44/23 号等文档中已有明确的 low4 退化记录。

## 3. 输入

`predictions.csv`，由 `spatial_meta_ce/evaluate.py` 产出，列为：

```
database, run, k, query_id, query_hash, true_cardinality, log_prediction
```

审计需要**同一次评估同时包含 k=0 与 k>0**，因为锚（K=0 预测）必须与适应后的预测来自同一 checkpoint、同一 query 集。`auditable_rows()` 按 `(database, run, query_hash)` 把 K=0 锚拼到 K>0 行上；缺锚直接报错，不静默丢弃。

### 3.1 两条实现约束（实测中发现）

1. **必须按 support run 分组**：同一 query 会在每个 run 里重复出现，直接合并会触发重复身份错误。因此每库输出 `per_run`（逐 run 报告）与 `across_runs`（各 run 标量的均值），**不合并原始行**。
2. **`predictions.csv` 不含 `n_tables`**：该列由 `evaluate.py` 的 CSV schema 决定，本轮不改它（改动会波及全部历史解析器）。缺失时审计仍可运行，报告 `table_buckets_available: false` 并省略表数直方图，**不猜测分桶**。若要启用表数分析，需在执行评估时额外导出 `n_tables` 侧表。

## 4. 实现

`scripts/failure_query_audit.py`（只读）：

```bash
python3 scripts/failure_query_audit.py --predictions runs/<run>/predictions.csv --k 20 --output 实验文档/results/p0-3-failure-audit-<date>/audit.json
```

输出结构：

```json
{
  "schema": 1,
  "purpose": "research-read-only-audit",
  "k": 20,
  "target_databases_read": [],
  "databases": {
    "<db>": {
      "per_run": {
        "run0": {
          "queries": 0, "worsened": 0, "worsened_fraction": 0.0,
          "worsened_by_pg_direction": {"over": 0, "under": 0, "tie": 0},
          "population_by_pg_direction": {},

                            "top1pct_share": 0.0, "shape": "none"},
          "table_buckets_available": false
        }
      },
      "across_runs": {
        "runs": 1, "worsened_fraction": 0.0, "top1pct_share": 0.0,
```

## 6. 实测结果（2026-10-20）

输入：`runs/p1-screen-20261020/baseline/last.pt`（ERM / seed42 / 4000 步 / sum-w64 / smooth_l1），
shots `[0, 5, 20, 100]`，5 个 support run，三源验证库全部 unique query。
预测导出：`scripts/export_source_predictions.py`（只读，`target_databases_read: []`）。

### 6.1 集中度：三库全部 `diffuse`

| 库 | K=20 恶化率 | K=20 top1% | K=100 恶化率 | K=100 top1% | 形状 |
|---|---|---|---|---|---|
| chembl | 43.65% | 0.110 | 40.74% | 0.115 | **diffuse** |
| legalacts | 49.21% | 0.058 | 47.28% | 0.056 | **diffuse** |
| telstra | 40.07% | 0.124 | 38.36% | 0.119 | **diffuse** |

按 §1.1 冻结判据：top1% 份额全部 < 0.25，恶化率全部落在 0.40–0.60 附近（telstra K=100 的 0.384 略低于下界，仍远非 concentrated）。**不是少数极端查询驱动，而是系统性弥散漂移。**

**直接含义**：P2-1 若只加几个结构标量（join 边数、度摘要），按 88 §3.3 的同一判据逻辑，**不太可能对症**——问题不在少数特征缺失的查询上，而是在所有查询上均匀分布的偏移。

### 6.2 PG 方向：恶化率与 PG 偏差方向强相关，且方向逐库相反

| 库 | PG 高估占比 | 高估查询恶化率 (K=20 / K=100) | PG 低估占比 | 低估查询恶化率 (K=20 / K=100) |
|---|---|---|---|---|
| chembl | 51.1% | 0.342 / 0.238 | 48.9% | **0.535 / 0.584** |
| legalacts | 36.0% | **0.921 / 0.873** | 64.0% | 0.251 / 0.247 |
| telstra | 57.5% | 0.262 / 0.195 | 42.5% | **0.588 / 0.639** |

**这是本轮最强的信号。** 两点值得注意：

1. **chembl 与 telstra 是"PG 低估 → 恶化"，legalacts 是"PG 高估 → 恶化"**，方向正好相反。说明模型没有学到"往哪边修"的通用规则，而是学了一个**库相关的偏移方向**；当某库的方向与训练分布主导方向相反时就系统性恶化。
2. legalacts 的 PG 高估查询恶化率高达 **0.92 / 0.87**——几乎全部恶化。而 legalacts 恰是历史文档（22 号 S7、14 号）反复点名的持续高尾库。

**这指向 P2-2（真实选择率审计）而不是 P2-1（结构标量）**：模型缺的不是 join 形状，而是**能指示"当前该往高估还是低估方向修"的信号**。真实选择率/条件相关性正是这种信号。

### 6.3 与 93 号假设的对照

| 93 §3 P0-3 假设 | 本轮证据 | 判定 |
|---|---|---|
| 恶化查询有稳定的可观测特征（表数、PG 方向、直方图缺失、join 形态） | **PG 方向**是最强特征，且逐库反号 | **部分证实** |
| 少数极端查询驱动 | top1% 份额 0.056–0.124，全部 diffuse | **否定** |
| 决定 P2-1 加什么特征 | 弥散 + 方向性 ⇒ 加结构标量不对症 | **改指向 P2-2** |
