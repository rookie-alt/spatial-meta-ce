# P1 映射消融：正式协议（冻结）

> 状态：**协议已冻结，9 次正式训练未启动**。启动需用户确认 GPU 资源与预算。
> 日期：2026-10-04。分支 `feat/mapping-model-gpu-smoke`。

## 1. 研究问题与主张边界

**问题**：join 列→表、filter 列→表的映射信息，对跨库基数估计的误差有多大贡献？

- **主比较**：真实映射 vs 边际保持打乱映射。两者同一 `sum_map` 架构、同参数量、同采样流，差异只在关联信息本身。
- **辅助比较**：真实映射 vs 原 `sum`。`sum_map` 参数更多（含 `mapping_fusion`/`fanout_fusion`），**容量混杂无法排除**，只能作为次要参考。
- **不可主张**：本消融完成后仍不能主张优于 PRICE；目标库在本阶段完全不参与。

## 2. 冻结配置

| 项 | 值 | 说明 |
|---|---|---|
| 臂 | `sum` / `true` / `shuffled` | `configs/p1_map_{sum,true,shuffled}.json` |
| 架构 | `sum` / `sum_map` / `sum_map` | true 与 shuffled 同架构同参数 |
| 映射模式 | — / `mapping` / `shuffled_mapping` | 均读 `runs/mapping-sidecars-source26-20261004` |
| 训练法 | `erm` | 延续 P0 固定预算 ERM-sum 血统 |
| seed | 42 / 43 / 44 | 由 runner 覆盖，共 9 次 |
| 预算 | `steps=4000`, `meta_batch=4` | 固定，不早停 |
| 早停参数 | `validate_every=100`, `patience=41` | 验证最多 40 次，`bad>=41` 永不成立 → **保证跑满 4000 步** |
| 验证计划 | `validation_seed=1729`, `validation_runs=5` | 三臂共用同一 query_hash 计划 |
| 优化器 / 损失 | Adam / SmoothL1 | 沿用现有循环 |
| 终点 | **`last.pt`** | 不用 `best.pt`（固定预算协议） |

`load_run_config` 会拒绝任何偏离上述冻结值的配置改动（架构、映射模式、steps/patience/method）。

## 3. 端点度量

`scripts/mapping_ablation_endpoint.py`，**源验证库 only**（chembl / legalacts / telstra）：

1. 每库取全部 unique query（按 `query_hash` 去重），**零样本**前向；
2. 按 join 表数分桶；**主指标 = 4+ 表桶的 q-error Q95**（口径同 `metrics.q_values`）；
3. 三库等权 macro 平均（与 `train.validate` 的「等库等 K 等重复」宏平均一致）；
4. 配对比较按 `query_hash` 逐条对齐，输出 `q95_ratio`、`left_better_fraction`、`mean_log_q_delta`；
5. **原样上报** sidecar 风险：每库 `sql_flags.multiple_filters`、`changed_fraction`、`unchangeable_rows`、`random_unchanged_rows`。打乱后未改变的比例直接限制对照强度，不得平滑或省略。

## 4. 配对不变量（runner 逐项核验，违反即停）

同 seed 的三臂必须共享：`sample_plan_digest`、`sample_plan_episodes`、`counts`、`validation_plan_hash`、`optimizer_steps`。
`true` 与 `shuffled` 必须共享：`initialization_hash`、`parameters`、sidecar 的 `manifest_hash`+`jsonl_hash`。
所有臂不得触及目标库。逐臂记录 device / GPU UUID / 峰值显存 / 耗时 / checkpoint SHA256。

## 5. 运行方式

```bash
# 先看矩阵，不占资源
python3 scripts/run_mapping_ablation.py --output runs/p1-mapping-ablation-20261004

# 确认资源后再执行（必须显式指定卡，不抢占）
CUDA_VISIBLE_DEVICES=5 python3 scripts/run_mapping_ablation.py \
  --output runs/p1-mapping-ablation-20261004 --execute --device cuda --gpu-index 5

# 训练完成后算端点
python3 scripts/mapping_ablation_endpoint.py \
  --runs runs/p1-mapping-ablation-20261004/ablation_runs.json \
  --config configs/p1_map_true.json --device cuda \
  --output runs/p1-mapping-ablation-20261004/ablation_endpoint.json
```

## 6. 实施期间发现并修复的问题

`StorePool` 默认 `max_open=4`，而映射 store 每次打开要完整解析 sidecar。实测：26 库同时常驻一次性 92.7 秒 / 2.99 GB，**单库重开 3.54 秒**。23 个训练库均匀随机采样下 LRU 几乎每步命中失败，4000 步 × 3 臂 × 3 seed 仅 sidecar 重解析就需上百小时。已在 `train()` 中改为 `max_open=len(sources)`（每个源库只打开一次），并以 `tests/test_mapping_ablation.py::ResidentStoreTests` 固化。
