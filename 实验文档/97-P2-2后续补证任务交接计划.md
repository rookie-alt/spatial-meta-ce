## 3. 任务 C：PRICE 同口径源侧对照（最便宜，约 30 分钟）

### 3.1 要回答什么

PRICE 在源验证库上的 Q95，与我们同一批查询的 Q95，到底差多少。当前 `price-lr-search-result.json` 里的 `per_db_mean_q95` 是**每 episode 64 条查询的 Q95 的均值**（25 个 episode：5 个 K × 5 个 run），不是全库 Q95，**不能与我们的全库数字并列**。

### 3.2 做法

写一个新脚本 `scripts/price_population_eval.py`（只读、不训练、不适应）：

1. 对三源验证库的**全部唯一查询**（chembl 50,000 / legalacts 49,504 / telstra 50,000）跑 PRICE K=0 推理；
2. PRICE 输出需经 `price_log_predictions()` 解码（vendor 输出是 `log1p(card)+1` 编码）；
3. 同一脚本读我们 seed42 的 K=0 预测作对照（或从 `predictions.csv` 读）；
4. 两边都算**全库单次 Q95 / Q50 / log-Q95**，再按 `n_tables` 分桶（1 / 2-3 / 4-5 / 6+）算 4+ 桶 Q95；
5. 明确记录：这不是 episode 均值，与 94/14 号的历史 PRICE 数字**不可直接比较**。

### 3.3 关键实现约束

- PRICE 的 `PriceAdapter` 需要 `maxima`（四组最大 token 数），从三库 cache manifest 的 `inspection.max_counts` 取逐库最大值。
- `price_support()` 用于把 support 转成 PRICE 标签编码，**K=0 时不需要 support**，但 `forward` 仍需要完整的 batch（含 `pg_log`、`groups`、`masks`、`counts`）。
- batch size 建议 128，CPU 单线程即可（PRICE 10.7M 参数，15 万条约 10–20 分钟）。
- 必须 `assert_source_database()` 拒绝目标库。

### 3.4 产物

```
实验文档/results/p2-2-price-population-<date>/
├── summary.json          # 三库 × {Q50,Q95,log_q95} × {all, 4+}
└── protocol.json         # 冻结口径、输入 sha256、target_databases_read: []
```

`summary.json` 结构建议：

```json
{
  "schema": 1,
  "target_databases_read": [],
  "metric": "unique-query population Q95 (single pass, NOT episode mean)",
  "databases": {
    "chembl": {
      "n": 50000,
      "ours_k0":   {"q50": 0.0, "q95": 0.0, "log_q95": 0.0},
      "price_k0":  {"q50": 0.0, "q95": 0.0, "log_q95": 0.0},
      "pg":        {"q50": 0.0, "q95": 0.0, "log_q95": 0.0},
      "bucket_4plus": {"ours_k0": {}, "price_k0": {}, "pg": {}}
    }
  }
}
```

### 3.5 验收

- [ ] 三库全部查询都参与，无裁剪
- [ ] PRICE 解码后的预测与 `pg_log` 同尺度（log 空间）
- [ ] `target_databases_read: []`
- [ ] 与历史 episode 均值并列时，文档明确标注两者不可比
- [ ] 单测覆盖：解码函数、分桶、目标库拒绝

### 3.6 预期与风险

- **预期**：我们可能在 chembl/legalacts 上接近或优于 PRICE（因为 PRICE 的 episode 均值是在小样本上算的，且我们在源侧有过拟合优势），但 telstra 大概率仍输。
- **风险**：若 PRICE 在全库上大幅优于我们，说明此前「源侧接近」的印象是 episode 粒度造成的错觉，**这会强化「打不过 PRICE」的结论，需要如实写**。

## 5. 任务 B：23 库跨库迁移检验（最贵，约 3–4 小时）

### 5.1 要回答什么

96 号的 LODO 只有 3 个库（chembl/legalacts/telstra），样本单位是「库」，n=3。要主张「方向信号跨库不迁移」，需要用更多库检验：**在 20 个训练库上学方向规则，能否预测第 21 个库？**

### 5.2 关键阻塞（先确认再动手）

**23 个源训练库没有 K=0 预测。** `predictions.csv` 只导出了三个验证库。要构造方向标签，必须先对 23 个训练库做 K=0 推理。

- 这是**新的推理任务**，不是训练，但仍需 GPU。
- 每库约 5 万查询，23 库约 115 万条，按 seed42 的导出速度（299 万行约 8 分钟）估算，**约 3–4 分钟**，可接受。
- 导出脚本 `export_source_predictions.py` 的 `assert_source` 允许任意非目标库，但需要传入 `--databases` 列表。

### 5.3 做法

1. **导出 23 库 K=0 预测**（只需 k=0，可改脚本或传 `shots` 单值以减少数据量）。
2. **构造标签**：`sign(log(true) − log_pred_K0)`，与 96 号定义完全一致。
3. **迁移检验**：leave-one-database-out，20 库训练 → 1 库测试，重复 23 次。
4. **对照**：同时报「随机猜多数类」基线。
5. **分桶**：按库规模、表数分布分层报告。

### 5.4 判定门槛（执行前冻结）

| 判据 | 门槛 |
|---|---|
| 23 次 LODO 的中位 AUC | < 0.55 → 支持「不迁移」 |
| 23 次 LODO 中 AUC < 0.5 的次数 | ≥ 5 → 说明存在系统性反向 |
| 与多数类基线比 | 迁移准确率超过多数类的库数 < 半数 → 支持「不迁移」 |

### 5.5 产物

```
实验文档/results/p2-2-crossdb-transfer-<date>/
├── summary.json      # 23 次 LODO 的 AUC / 准确率 / 多数类基线
└── protocol.json
实验文档/99-跨库方向迁移检验.md
```

### 5.6 风险与成本

- **若结果显示部分库能迁移**，96 号的结论需要修正为「迁移性因库而异」，这本身也是有价值的发现。
- **成本最高**：导出 23 库 + 23 次训练评估，估计 3–4 小时，且需要 GPU 空闲窗口。
- **建议在任务 C、A 完成后再决定是否执行**：如果 A 显示三 seed 不稳定，B 就没有意义。

## 11. 任务 C 执行结果：PRICE 同口径源侧对照（2026-10-20）

> 本节是实跑结果。数字全部来自服务器实跑输出，产物在
> `results/p2-2-price-population-20261020/{summary.json, protocol.json}`。
> 脚本 `scripts/price_population_eval.py`，单测 `tests/test_price_population_eval.py`（21 项），
> 分支 `experiment/p2-2-price-population-20261020`。
> **只读推理，不训练、不适应、不选 checkpoint，`target_databases_read: []`。**

### 11.1 口径

三源验证库的**全部唯一查询**（chembl 50,000 / legalacts 49,504 / telstra 50,000，合计 149,504）
各跑一次 K=0 推理，无 support 采样、无 episode 结构。三个估计量共用同一批查询、同一套指标：

| 估计量 | 来源 |
|---|---|
| `ours_k0` | seed42 baseline checkpoint 零样本，读 `runs/p0-3-audit-20261020/predictions.csv` 的 K=0 行（299 万行导出的子集） |
| `price_k0` | 提供的 PRICE 权重零样本，原生输出经 `price_log_predictions()` 从 `log1p(card)+1` 解码到 `log(card)` |
| `pg` | cache 里的原始 PostgreSQL 估计（`cards[:,1]`），非 K=0 锚 |

指标沿用 14 号主表口径：标准 **unique-query Q95**（`exp(|max(log_pred,0) − log(max(true,1))|)` 的 95 分位），
不用 all-rows，也不用 `(pred+1)/(true+1)` 的 PRICE shifted 口径；`price_shifted_*` 作为复算并列在 `summary.json` 里，
两者在本轮排序完全一致，结论不依赖指标选择。

PRICE 的输入归一化 `maxima` 取三库 `inspection.max_counts` 的逐元素最大值 `[11,12,7,10]`，
与源侧 PRICE 基线（`price_lr_search.py`）同规则。PRICE 10,709,330 参数，
checkpoint sha256 `4f889c4df269d1bca5a50dadd83de7c801a607fe84228b6c21fb3371ae053f92`。

| legalacts | 49,504 | **9.712** | 11.817 | 26.000 | 1.217 |
| telstra | 50,000 | 7.994 | **5.654** | 6.974 | 0.707 |
| **macro** | 149,504 | **28.646** | 16.965 | 59.679 | 0.592 |

4+ 表桶（`n_tables ≥ 4`）Q95：

| chembl | 33,947 | 104.818 | **46.644** | 354.839 | 0.445 |

| telstra | 20,311 | 11.941 | **8.194** | 11.000 | 0.686 |
| **macro** | | **44.144** | 25.482 | 138.613 | 0.577 |

Q50 与 log-Q95（macro）：ours 2.035 / 2.858，price 1.705 / 2.570，pg 1.726 / 3.395。

**判定**：Q95 上我们只在 legalacts 领先（1.22×，4+ 桶 1.38×），chembl 落后 2.04×（4+ 桶 2.25×），
telstra 落后 1.41×。在项目自己的主指标 `macro_four_plus_q95` 上，**PRICE 比我们好 42.3%**（25.48 vs 44.14）。
分桶看，chembl 的 2-3 / 4-5 / 6+ 三桶 PRICE 全部领先（8.71 / 40.44 / 65.52 vs 18.07 / 91.45 / 134.67），
差距随表数单调放大。

**一个新事实**：我们 K=0 的**中位数在三个源库都不如原始 PG**（2.589 / 1.935 / 1.580 vs PG 2.276 / 1.512 / 1.390）。
我们相对 PG 的价值集中在尾部（chembl Q95 68.2 vs 146.1、legalacts 9.71 vs 26.0），在 chembl 的 4+ 桶更是
104.8 vs 354.8；但 telstra 的 4+ 桶 PG（11.00）反而略好于我们（11.94）。

### 11.3 与历史 episode 均值的关系：粒度不是全部原因

97 §0 列的第三个薄弱点是「PRICE 的源侧数字是 episode 均值，与我们全库 Q95 不可比」。
本节把两侧都摆出来，但必须同时说清：**episode 数字是 K≥5 已适应、每 episode 64 条查询的 Q95 均值；
population 数字是 K=0 零样本、单次全量。两者在粒度和适应状态上同时不同，不构成纯粒度对照。**

| 库 | 我们 episode (K≥5) | PRICE episode (K≥5) | 我们 population (K=0) | PRICE population (K=0) | episode 比值 | population 比值 |
|---|---:|---:|---:|---:|---:|---:|
| chembl | 53.271 | 28.759 | 68.233 | 33.426 | 0.540 | 0.490 |
| legalacts | 9.531 | 9.488 | 9.712 | 11.817 | 0.995 | 1.217 |
| telstra | 8.395 | 5.384 | 7.994 | 5.654 | 0.641 | 0.707 |

- 我们 episode 均值来自 `runs/p1-screen-20261020/baseline/history.json` 末条（step 4000）的 75 条验证记录
  （3 库 × 5 个 K × 5 个 run，每条 n=64）的 q95 均值；PRICE episode 均值来自
  `results/price-lr-search-result.json` 的 `trials[0]`（`inner_lr=1e-6`，该 lr 是源验证选出的）。
- **方向一致的库**：chembl、telstra 在两种粒度下都是 PRICE 领先，且比值都落在 0.49–0.71。
  也就是说「chembl / telstra 上我们明显落后 PRICE」**不是粒度错觉**，只是被量纲放大了。
- **方向翻转的库**：legalacts 在 episode 粒度是打平（0.995），在 population 粒度是我们领先（1.217）。
  这是唯一由粒度改变结论的库，也是我们唯一领先且稳定的库。
- 结论：**「源侧接近 PRICE」这个印象只在 legalacts 成立**，而且只在 population 粒度成立。
  97 §3.6 预判的「风险情形」（PRICE 在全库上大幅优于我们，说明此前印象是 episode 粒度造成的错觉）
  **部分兑现**：chembl 确有大差距，但比值与 episode 粒度几乎相同，所以差距本身是实的，不是粒度造出来的。

### 11.5 边界（不能写成什么）

- **不能**把本节的 population 数字与 14 / 94 号的目标库数字并列：库不同、split 不同（源验证 vs 目标测试）。
- **不能**把本节数字与 `price-lr-search-result.json` 的 `per_db_mean_q95` 并列：episode 均值 vs 全库单次。
- **不能**把 population K=0 与 episode K≥5 的差值说成「适应带来的提升」：两者粒度与适应状态都不同。
- **不能**把本节的 `bucket_4plus` 读成 14 号主表里的 `four_plus_tables`：本节是单库分桶后各自算 Q95，
  14 号是三库各自算再 macro。
- `ours` 侧是**单 seed（42）**，本节结论标 `needs_evidence`；seed 覆盖由任务 A 补。
- 源侧三库的表数都 ≥ 2，`n_tables = 1` 桶在三库都是空桶（`n=0`，指标记 `null`），不是漏算。
- 推理耗时不属于数据库端到端加速证据；本节只测精度。
