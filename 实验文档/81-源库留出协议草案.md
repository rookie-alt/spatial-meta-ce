## 1. 动机与被解决的问题

三个源验证库 `chembl/legalacts/telstra` 已被 S1–S8 与 Meta65 多轮开发筛选反复使用。继续在这三库上换 seed、换 K 或换算子，任何"改善"都无法区分**真实跨库泛化**与**选择偏差**：同一批库既用于选策略又用于报告收益。

本协议的目标是提供一条**尚未作为评估库使用过、且不被本协议任何新臂训练**的源侧评估信号：从 23 个训练库中固定留出两个库，在所有新臂（含元训练）中完全排除，作为新的源侧"准留出"评估集。

**边界声明**：65 号方案已明确"已被 checkpoint 训练过的库不称新留出"。本协议留出的是**尚未作为评估库使用过**的训练库，它们仍会被**历史** checkpoint 曝光；本协议只保证**新臂**不再训练它们，不宣称统计意义上完全干净的 holdout，也不等同于目标库盲测。

完整 26 库表见[附录 A](#附录-a26-库只读盘点完整记录)。与主口径相关的关键事实：

备选组合与理由（不构成推荐）：

## 3. 协议设计（待确认项全部标注）

### 3.1 训练侧改动

| 项目 | 旧（65 号） | 本协议 |
|---|---|---|
| 元训练训练库 | 23 | 21（排除 2 个留出库） |
| 源验证库（策略选择） | chembl/legalacts/telstra | 不变 |
| 新源侧评估库 | 无 | 2 个留出库 |
| 目标库 | imdb/stats/genome/ergastf1 不进任何环节 | 不变 |

关键约束：

- 留出库不得进入训练采样、验证监控、超参数选择、适应策略选择或 checkpoint 选择。
- 留出库的评估**只在实验全部冻结后进行一次**，不据其结果改任何臂；若需改方案，须另立协议。
- 新臂的 `data signature`（训练库集合哈希）必须与历史臂不同，并在 binding 中记录。

### 3.2 待用户确认的开放问题

1. **留出库组合**：建议 `hepatitis`+`sakila`；是否接受，或改用高基数/低基数备选组合。
2. **评估算子的选择来源**：部署算子（`none`/`head3`）仍只由 `chembl/legalacts/telstra` 决定，留出库只做报告。需确认这一"选择与报告分离"设计。
3. **对照臂数量**：是否仍跑 R/T 双臂（head/3 vs all/3），或先只跑当前基线 R 单臂建立留出库基线。**后者成本更低且信息更直接**：先知道基线在留出库上的绝对水平和迁移幅度，再决定是否值得做干预臂。
4. **K 集合**：是否只做 K20（与 65 号首轮一致，便于与 `no_candidate` 结论对照），或做完整 5 个 K。
5. **预算上限**：需按第 4 节实测后冻结。

## 4. 预算与执行边界（均为建议，未授权）

- 65 号实测参考：R 臂 4000 步训练+60 cell 评估共 4742.28 秒，峰值 RSS 4.61 GiB，输出 190 MB。留出库训练库从 23 减到 21，单步成本略降，总时长预计同量级。
- 建议沿用冻结预算结构：父监督总上限 14400 秒、RSS 12 GiB、VRAM 8 GiB、输出 1 GiB；实施前须重新实测估算，不满足即启动前 blocked。
- 单张现场空闲 GPU、显式 `CUDA_VISIBLE_DEVICES`/UUID、`CUBLAS_WORKSPACE_CONFIG=:4096:8`、单线程；忙则 blocked，不抢占/排队/换卡。
- 非有限/错配/OOM/超时/hash 失败即停止，只清理自有进程组，不自动 retry/resume/补臂。

## 5. 候选判定（事前冻结草案，需确认）

沿用 65 号门槛结构，但把"三库"替换为"三验证库选策略 + 两留出库报告"：

1. 策略与候选**只**由 chembl/legalacts/telstra 决定；留出库结果不参与选择。
2. 若在验证库通过候选门槛，须同时报告两留出库的 4+ 表 Q95/Q50 与主桶值，作为**描述性**跨库证据。
3. 留出库显著退化（建议阈值与 65 号一致的 1.10 倍护栏）时，结论须写为"验证库通过但留出库退化"，**不得**据此声称跨库泛化改善。
4. 未在验证库通过时，留出库数据仍应归档，作为后续协议的参考，不删除不利结果。

## 6. 实施顺序（每一步单独授权）

1. 用户确认第 3.2 节开放问题 → 冻结协议文本与 SHA。
2. 实现：新增独立配置/runner/证据目录，不改旧冻结文件；TDD 覆盖留出库完全排除（训练采样、验证监控、checkpoint 选择三层断言）、数据 signature 变更、目标库禁入、分母与配对。
3. CPU 验收 → GPU 预检（现场查空闲卡）。
4. 冻结 code/input SHA 与新 binding，向用户展示确切 SHA 请求一次性执行确认。
5. 单次正式运行 → 独立认证 → 归档精简证据。

## 7. 局限

- 留出库仍被历史 checkpoint 训练过，不是全新数据库；本协议提供的是"新臂未训练"的证据，不是完全干净的统计 holdout。
- 21 个训练库的元训练质量可能低于 23 库，"泛化改善"与"训练数据减少"在本设计中仍部分混杂；若两库留出后验证库主指标同时明显恶化，须先报告该混杂，不得只报留出库收益。
- 单 seed、单 K 结论的强度与 65 号相同，不构成跨库确认。
- 未做目标库评估，不与 PRICE 做同冻结对照，无端到端加速主张。
