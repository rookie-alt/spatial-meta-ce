## 2. 数据链正确性（门槛 1 与 1b）

1. **oracle 自洽（门槛 1）**：600 条抽样查询上，`C_cond`（逐键频次点积）与 `exact`（pandas inner merge 计数）**逐条相等，600/600**。
2. **快照与 workload 一致（§7.1）**：把 `exact` 与 workload 里记录的 `true_card` 相比，**最大相对偏差 0.0，600/600 精确相等**。
3. **独立复算（§9.4）**：每库前 20 条、共 60 条，用纯 Python 字典计数重算，不经过 pandas groupby 或 merge，全部与上面两者一致。

第 2 条的意义需要限定：它证明的是**在本轮 600 条两表单键等值、AND-only 字面量谓词、三个库的抽样上**，按 DDL 类型 + `read_csv(sep='|', quotechar='"', escapechar='\\', keep_default_na=False, na_values=['NULL'])` 这套语义能逐条重现 `true_card`。它**不能**推广为"该快照的行级语义已被全面校验"——三表以上、OR、NULL、跨类型连接都没有被这条证据覆盖。

> 说明：`C_cond` 是 oracle，它等于精确计数是构造使然，这条门槛检验的是实现而不是信息量。信息量由门槛 3 检验。
>
> 另需明确一条实现边界：`exact`、`C_cond`、独立复算三者共享同一套「键值如何比较」的假设，所以门槛 1 **看不见**语义层面的错误（例如 int 与 str 键被错误对齐）。这类错误的唯一兜底是门槛 1b 对 `true_card` 的比对——它本轮为 0.0，说明这条兜底没有被触发。

## 3. 覆盖（门槛 2）

| 库 | 唯一查询 | eligible | 可表示率 | 抽样 | 抽样可表示 | run 阶段拒绝 |
|---|---:|---:|---:|---:|---:|---:|
| hepatitis | 50,000 | 3,060 | **6.12%** | 200 | 200/200 | 0 |
| carcinogenesis | 50,000 | 14,842 | **29.68%** | 200 | 200/200 | 0 |
| basketball | 50,000 | 7,065 | **14.13%** | 200 | 200/200 | 0 |

门槛 2 的判据在代码里明确为：**每库抽样查询中以原 SQL 重新解析得到的 spec 与冻结 spec 完全一致的比例 ≥95%，且 run 阶段没有类型性拒绝**。实际 3×200/200、`rejected.json` 为空。

**hepatitis 的 6.12% 是可表示率的下限，也是本结果外推的最大限制**：该库 93.88% 的查询是三表及以上，G1 的两表口径覆盖不到。三库的表数分布已冻结在 `plan.json` 的 `table_count_histogram`。

**过滤连接键的比例为 0**，这次是落盘数据而非临时计算：`plan.json` 每库 `filters_join_key_count = 0`（分母 3,060 / 14,842 / 7,065），抽样 600 条同样全为 `false`。因此 §7.3 要求的「是否过滤连接键」分桶在本轮**退化为单桶、未被检验**。这些 workload 的过滤条件全部落在非连接列上，条件信息只能通过列间相关性间接起作用。

> 一处需要读者注意的归类效应：`analyze()` 先判表数，所以三表以上的查询即使带 OR / LIKE / LEFT JOIN，也一律记为 `table_count_N`。因此"unsupported 原因只有 `table_count_N`"只能说明**两表查询里**没有这些模式，不能说明 workload 整体没有。

## 4. 主对照（门槛 3）

600 条抽样查询，q-error 定义 `exp(|log max(est,1) − log max(true,1)|)`：

| 估计器 | median | Q95 | max | mean |
|---|---:|---:|---:|---:|
| B0 独立性 | 1.167 | 4.645 | 36.00 | 1.951 |
| C_uncond | 1.067 | 2.481 | 36.39 | 1.601 |
| **C_cond（oracle）** | **1.000** | **1.000** | **1.00** | **1.000** |

| 门槛 3 判据 | 实际比值 | 门槛 | 结果 |
|---|---:|---:|---|
| Q95 比值 `C_cond / C_uncond` | **0.403** | ≤ 0.50 | ✅ |
| median 比值 `C_cond / C_uncond` | **0.937** | ≤ 0.50 | ❌ |

逐库：

| 库 | C_uncond median | C_uncond Q95 | C_cond median | C_cond Q95 |
|---|---:|---:|---:|---:|
| hepatitis | 1.000 | 1.242 | 1.000 | 1.000 |
| carcinogenesis | 1.186 | 3.524 | 1.000 | 1.000 |
| basketball | 1.163 | 5.040 | 1.000 | 1.000 |

**hepatitis 上 C_uncond 的中位数已经精确（1.000）、Q95 只有 1.242**——这一库几乎不提供条件信号；另外两库的差距集中在尾部。

`C_uncond` 的两个因子都已落盘（`query_results.csv` 的 `domain` 与 `collision` 列），可脱离脚本独立复算：`C_uncond = n_left_f · n_right_f · collision`，`B0 = n_left_f · n_right_f / domain`。

读法：在 carcinogenesis 与 basketball 上，过滤越狠 `C_uncond` 的尾部越差；hepatitis 几乎全程精确。`C_cond` 在所有桶里都是 1.000。中位数之所以过不了 50% 门槛，是因为 **C_uncond 在中位数上本来就基本正确**（全表 1.067，分桶后 1.000–2.802），没有留给条件化 50% 的空间。

**两条必须一起读的限定**：

1. **桶级趋势不等于查询级规律。** 查询级 `Spearman(选择率, q_uncond) = +0.104`（`Pearson = −0.12`），方向与"选择率越低越糟"相反且很弱。桶级 Q95 由少数尾部查询撑起，`<1e-3` 桶 n=29 里 27 条来自 basketball、2 条来自 carcinogenesis，hepatitis 在该桶为 0。
2. **表对分布在总体里本来就高度集中，抽样基本忠实反映了它。** hepatitis 全量 eligible 中 `indis|rel12` 占 **2,762/3,060（90.3%）**，抽样是 179/200（89.5%）；carcinogenesis 前三大表对占 12.6% / 12.2% / 11.7%，basketball 为 13.5% / 13.2% / 12.7%。所以分桶表里"库"与"选择率"的共线来自 **workload 本身的结构**，不是等距抽样引入的偏差——但它的后果一样：桶与库仍然不可完全分离。

`filters_join_key` 全为 `false`（见 §3），该维度在本轮无对照。

> 分桶定义在 114 号 §7.3 已写明（按选择率、按是否过滤连接键），本轮据其实现；分桶不参与 go/no-go 判定，`breakdown.json` 自带同样的声明。

## 8. 这些数字意味着什么，不意味着什么

**是**：

- 在三个小源库的两表查询上，「过滤后表大小 × 未过滤键碰撞概率」这个非条件估计器**在中位数上已经相当准**，条件化能带来的中位收益只有 6.3%。
- 条件信息的价值**在分桶层面集中在尾部**：整体 Q95 从 2.481 降到 1.000；选择率 <1e-3 桶从 13.047 降到 1.000。查询级相关性弱（ρ=+0.10），不要把桶级趋势读成逐查询规律。
- 按事前冻结的判据，这**不足以**支撑进入摘要构建（G1b）与新架构实现。

**不是**：

- 不是「联合分布没用」。反例门槛、Q95 门槛都通过了，条件频数确实携带信息。
- 不是「新架构一定不行」。本协议只覆盖两表、单键、等值、非连接键过滤；三表以上（hepatitis 93.9%、carcinogenesis 70.3%、basketball 85.9%）完全没测。
- 不是「q-error 指标口径」的问题。q-error 用的是项目既有定义（`metrics.py:q_values`），与本项目所有历史数字同口径。

**需要单独说明的一点**：项目的主指标一直是 unique-query Q95，而本轮失败在 median。这不是可以现场调整门槛的理由——门槛在 2026-11-02 就冻结了，事后因 median 未过而改判据属于移门柱。若要继续，正确做法是**另立新协议、新 SHA，并在其中显式披露「上一版门槛的 median 条件未通过」**，而不是修改本文件。

## 9. 边界

- 只覆盖两表单键等值内连接；多表、环、自连接、多键、非等值、OR/NULL 语义均未实现。
- 三个主库最大 44,822 行，**抽样涉及的最大单表为 23,751 行**（basketball）；不能代表大库的倾斜与高基数键，也不外推到其余 23 个源库。
- eligible 查询中过滤连接键的比例为 0%，条件信息的最强场景未被检验。
- `C_cond` 是 oracle，需要读原表；它不代表可部署成本，可部署性属于 G1b，本轮未做。
- 目标库 `imdb/stats/genome/ergastf1` **未解压、未读取、未进入任何步骤**；脚本在两处硬性拒绝这些库名。
- `/gly/weilin/PRICE-master` 只读，未修改；冻结统计未重算。
- 抽样为每库 200 条等距抽取，`plan.sha256` 冻结后未改选。
- 跨类型连接键（如 int 列对 varchar 列）在实现里被显式拒绝而不是强行转换；本轮三库的 join 键对全部同类型，未触发。
